## 1. 目的與成功標準

### 目的

一個迷你版的跨幣別轉帳後端:多幣別帳戶、複式記帳、鎖定匯率的報價、冪等的轉帳 API。
作為應徵金融科技後端職位的作品集專案,同時是學習 Java 與 Spring Boot 的載體。

### 成功標準

1. 面試官讀完 README 與程式碼,能看出作者理解支付系統的核心難點:金額精確、帳務守恆、冪等、併發、外部依賴失效
2. 每一個設計決定都能回答「為什麼」;本文件第 10 節列出這些決定與理由
3. 別人只要一個指令(`docker compose up`)就能在本機啟動,再透過 Swagger UI 試用,不需要寫程式或使用 curl
4. 「錢不會算錯」由不變量測試證明,而不只是由幾個例子示範

### 刻意不做的事(第一版)

| 不做 | 理由 |
|---|---|
| 登入驗證 | 與核心問題(帳務正確性)無關;顧客 id 直接放在網址 |
| 前端畫面 | 應徵後端職位;Swagger UI 已足夠試用 |
| 微服務拆分 | 一人專案做不完分散式交易;改以清楚的模組邊界表明「會沿哪裡拆」 |
| 實際出款、webhook、非同步流程 | 轉帳只在內部帳本完成,同步回應 |
| 「對方收到多少」的反向報價 | 只支援「我要匯出多少」 |
| 部署上線 | 第一版之後再決定;屆時先查證費用 |

## 3. 架構

模組化的單體應用:一個 Spring Boot 程式、一個 PostgreSQL 資料庫。依業務切成四個模組:

| 模組 | 職責 | 對外介面 |
|---|---|---|
| `account` | 顧客、幣別帳戶、餘額 | 開戶、查餘額、鎖定帳戶 |
| `ledger` | 複式記帳:寫入分錄、檢查平衡 | 記一筆帳務事件 |
| `fx` | 匯率抓取、快取、報價 | 取得報價、查詢報價 |
| `transfer` | 轉帳流程、冪等 | 執行轉帳、查詢轉帳 |

規則:模組之間只透過對外介面呼叫,不直接讀寫彼此的資料表。`transfer` 是唯一會協調其他三個模組的地方。

為什麼不是微服務:跨服務轉帳會遇到分散式交易(需要 saga 等模式),對一人、邊學 Java 的第一版而言成本過高。單體讓扣款與入帳能放在同一個資料庫交易裡。模組邊界即是日後拆分的邊界。

## 4. 金額

- 以**整數的最小貨幣單位**儲存與計算(Java `long`、SQL `BIGINT`):100.50 EUR 存為 `10050`,100 JPY 存為 `100`
- 每種貨幣的小數位數取自 `java.util.Currency`(ISO 4217)
- 只有匯率換算使用 `BigDecimal`,算完立即依明定的規則轉回整數
- 金額永遠不經過 `float` / `double`;外部 API 回傳的匯率(JSON 數字)也直接解析為 `BigDecimal`
- API 的金額一律以**字串**表示(`"100.50"`)並附幣別,不用 JSON 數字

## 5. 資料模型

### 資料表

| 資料表 | 用途 | 主要欄位 |
|---|---|---|
| `customers` | 顧客 | id、名稱、建立時間 |
| `accounts` | 某顧客的某幣別帳戶,或系統帳戶 | id、顧客 id(系統帳戶為空)、幣別、類型、餘額快取、建立時間 |
| `journal_entries` | 一筆帳務事件(一次入金、一次轉帳) | id、類型、建立時間 |
| `postings` | 記帳分錄 | id、事件 id、帳戶 id、金額(有正負號)、幣別 |
| `quotes` | 鎖定的報價 | id、來源/目標幣別、來源金額、中間價、手續費、目標金額、匯率日期、到期時間、狀態 |
| `transfers` | 一次轉帳 | id、冪等鍵(唯一)、請求內容雜湊、報價 id(唯一)、來源/目標帳戶、事件 id、狀態、建立時間 |
| `deposits` | 一次模擬入金 | id、冪等鍵(唯一)、請求內容雜湊、帳戶 id、金額、事件 id、建立時間 |
| `fx_rates` | 抓回來的匯率 | 基準幣別、目標幣別、匯率、匯率日期、抓取時間 |

### 關於報價與顧客

報價不綁定顧客(第一版無登入驗證),任何人持有報價 id 即可使用;使用時檢查幣別與帳戶相符。加入驗證後應改為綁定顧客。

### 帳戶類型

- `CUSTOMER`:顧客的幣別帳戶,餘額不可為負
- `FEE_REVENUE`:系統手續費收入,每種幣別一個
- `FX_POSITION`:系統換匯部位,每種幣別一個,可為負
- `FUNDING`:模擬外部銀行的入金來源,每種幣別一個,可為負

系統帳戶在資料庫遷移時為支援的幣別建立。

### 記帳規則

1. 每筆帳務事件的分錄,**依幣別分組後,每組加總必須為 0**
2. 分錄只能新增,不能修改或刪除;更正以反向分錄處理
3. `accounts.balance` 是快取,必須恆等於該帳戶所有分錄的加總;兩者在同一個交易內更新
4. 顧客帳戶的餘額不可為負

### 範例:跨幣別轉帳

100 EUR → GBP,手續費 0.50 EUR,匯率 0.85:

| 帳戶 | 幣別 | 金額(最小單位) |
|---|---|---|
| 匯款人 EUR(`CUSTOMER`) | EUR | −10000 |
| 手續費收入(`FEE_REVENUE`) | EUR | +50 |
| 換匯部位(`FX_POSITION`) | EUR | +9950 |
| 換匯部位(`FX_POSITION`) | GBP | −8457 |
| 收款人 GBP(`CUSTOMER`) | GBP | +8457 |

99.50 × 0.85 = 84.575 → 無條件捨去為 84.57。

### 範例:入金

| 帳戶 | 幣別 | 金額 |
|---|---|---|
| 入金來源(`FUNDING`) | EUR | −10000 |
| 顧客 EUR(`CUSTOMER`) | EUR | +10000 |

## 6. 匯率與報價

### 匯率來源

- 定義介面 `RateSource`;正式執行時的實作呼叫 Frankfurter(ECB 資料),測試時換成固定匯率的實作
- **定時抓取**(預設每小時),結果連同匯率日期與抓取時間存入 `fx_rates`;報價只讀資料庫,不在請求當下呼叫外部 API
- 抓回的資料先驗證:匯率必須為正數、必要幣別必須存在;不合格的資料整批拒收並記錄,繼續沿用舊匯率
- **最長可用期限**:最新一筆匯率的匯率日期距今超過上限(預設 4 天,涵蓋週末加連假)時,停止產生新報價,回傳 503
- 支援的幣別 = ECB 有公布的幣別
- 交叉匯率:ECB 皆以 EUR 為基準,A→B = (EUR→B) ÷ (EUR→A);以 `BigDecimal` 計算,除法使用 `MathContext.DECIMAL128`(34 位有效數字)
- 報價中的匯率四捨五入(HALF_EVEN)到**小數 10 位**後存入報價;目標金額一律以**存下來的那個匯率**計算,確保顧客看到的匯率就是實際使用的匯率
- 「今天」一律以 UTC 日期計算

### 報價規則

- 匯率使用中間價,**不加價**
- 手續費 = 來源金額 × 固定比例(預設 0.5%,可設定),**無條件進位**到最小單位
- 目標金額 = (來源金額 − 手續費)× 匯率,**無條件捨去**到最小單位
- 同幣別也走報價,匯率為 1
- 有效期預設 10 分鐘,可設定
- 報價狀態:`OPEN` → `USED`;過期與否由到期時間判斷,不另設狀態
- 時間一律由注入的 `java.time.Clock` 取得,測試可固定時間

捨入方向的理由:手續費進位、收款金額捨去,公司永遠不會付出比算式結果更多的錢;而兩個數字都在報價時明確告知顧客。

## 7. API

| 方法與路徑 | 用途 | 冪等鍵 |
|---|---|---|
| `POST /customers` | 建立顧客 | |
| `POST /customers/{id}/accounts` | 開幣別帳戶 | |
| `GET /customers/{id}/accounts` | 查所有幣別餘額 | |
| `POST /accounts/{id}/deposits` | 模擬入金 | 必填 |
| `POST /quotes` | 取得報價 | |
| `GET /quotes/{id}` | 查詢報價 | |
| `POST /transfers` | 以報價執行轉帳 | 必填 |
| `GET /transfers/{id}` | 查詢轉帳 | |
| `GET /accounts/{id}/statement` | 帳戶明細(分頁) | |

- 冪等鍵以 HTTP 標頭 `Idempotency-Key` 傳遞
- 同一顧客同一幣別只能有一個帳戶;重複開戶回傳 409

### 錯誤回應

格式為 RFC 9457(`application/problem+json`),並附穩定的錯誤代碼欄位供程式判斷。

| 狀況 | 狀態碼 |
|---|---|
| 輸入格式錯誤、缺少冪等鍵 | 400 |
| 找不到顧客、帳戶、報價、轉帳 | 404 |
| 冪等鍵相同但內容不同;報價已使用;重複開戶 | 409 |
| 餘額不足、報價過期、幣別與帳戶不符 | 422 |
| 匯率過舊無法報價;等待帳戶鎖逾時 | 503 |
| 其他未預期錯誤 | 500(細節只寫入日誌) |

## 8. 轉帳流程

整個流程在**單一資料庫交易**中完成,任何一步失敗即全部復原:

1. **冪等**:以冪等鍵與請求內容雜湊寫入 `transfers`(狀態 `PENDING`)。冪等鍵有唯一限制:
   - 鍵已存在且雜湊相同 → 回傳既有的轉帳結果
   - 鍵已存在但雜湊不同 → 409
   - 兩個相同請求同時到達 → 只有一個寫入成功;另一個等對方交易結束後讀取其結果
2. **報價**:必須存在、`OPEN`、未過期,且來源/目標幣別與兩個帳戶相符
3. **鎖定**:以 `SELECT ... FOR UPDATE` 鎖定所有涉及的帳戶,**一律依帳戶 id 由小到大**,避免死結;設定鎖等待逾時
4. **餘額**:匯款人帳戶餘額 ≥ 來源金額
5. **記帳**:寫入事件與分錄、更新餘額快取、報價改為 `USED`、轉帳改為 `COMPLETED`

**失敗的請求不被冪等機制記住**:交易復原時,第 1 步寫入的紀錄也一併消失。例如因餘額不足而失敗,入金後以同一個冪等鍵重試,會被當作新請求處理。只有成功的轉帳受冪等保護,因為那才是需要防止重複扣款的情況。

入金流程相同,但沒有報價步驟,且不需檢查餘額。

## 9. 測試策略

| 類型 | 內容 |
|---|---|
| 單元測試 | 金額與最小單位換算、手續費進位、收款金額捨去、交叉匯率、報價過期(固定 `Clock`) |
| 不變量測試 | 以 jqwik 隨機產生入金、報價、轉帳序列,每步之後檢查:(1) 所有分錄依幣別加總為 0;(2) 每個帳戶的餘額快取等於其分錄加總;(3) 顧客帳戶餘額皆不為負 |
| 併發測試 | 多執行緒同時從同一帳戶轉帳:餘額不為負、總額守恆;多個請求同時帶同一冪等鍵:只產生一筆轉帳 |
| 整合測試 | Testcontainers 啟動真的 PostgreSQL;不使用 H2,因為列鎖行為必須與正式環境一致 |
| 匯率來源測試 | WireMock 模擬逾時、HTTP 500、格式錯誤、缺幣別、負匯率 |
| API 測試 | 每個端點的狀態碼與 problem+json 內容 |

CI(GitHub Actions)在每次 push 執行全部測試。

## 10. 設計決定與理由(面試題材)

| 決定 | 理由 | 放棄的做法 |
|---|---|---|
| 整數最小單位 | 不會有浮點誤差或半分錢 | `double`;全程 `BigDecimal` |
| 複式記帳、分錄只增不改 | 每一分錢都有來源與去向,可稽核 | 直接修改餘額 |
| 餘額快取 + 不變量測試 | 查餘額快,又能證明快取正確 | 每次加總所有分錄 |
| 中間價 + 透明手續費 | 顧客清楚知道匯率與費用各是多少,沒有藏在匯率裡的成本 | 在匯率上加價 |
| 手續費進位、收款捨去 | 公司不會超付;兩者皆事先告知 | 四捨五入 |
| 報價鎖定匯率與期限 | 顧客確認的金額就是實際執行的金額 | 轉帳時才取匯率 |
| 冪等鍵 + 內容雜湊 | 網路重試不會重複扣款;內容不同能被發現 | 只靠客戶端不重送 |
| 失敗不記入冪等 | 餘額不足等暫時性失敗在修正後可重試 | 連失敗結果都快取 |
| 列鎖並依 id 排序 | 防止超扣,且避免死結 | 樂觀鎖(衝突時重試成本高、測試較難) |
| 匯率定時抓取、報價只讀資料庫 | 外部 API 斷線不影響報價;有明確的過期上限 | 每次報價即時呼叫 |
| 模組化單體 | 一人可完成;單一交易保證帳務一致;邊界即日後拆分點 | 微服務 |
| 真的 PostgreSQL 做測試 | 鎖與交易行為與正式環境一致 | H2 |
